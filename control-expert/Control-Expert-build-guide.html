Automation · Control Expert build

Programming the M580 for the demo rig

How to build the EcoStruxure Control Expert project for the rig: a BMEP584040S safety CPU with its BMEP58CPROS3 coprocessor, a BMENOC0311 scanning the SIG300 and the ATV930, and a BMECRA31210 eRIO drop linked over fiber by two BMXNRP0200s. The program reads the SICK MPB10, runs the ATV930, works out a stack-light state for the dashboard and talks to the Machine Health dashboard. The program is six Structured Text sections in this folder; this page is the order to put them together and test them.

Safety first. The E-stop is hard-wired to the ATV930’s STO inputs and never goes through the PLC or the dashboard. Guard the motor and the unbalance weight. Test every drive step with the motor uncoupled and a low speed limit (iMaxSpeed).

1What’s in the folder

00_IO_Map→01_MPB10_Decode→02_Dashboard_In→03_ATV930_Control→04_Dashboard_Out→05_IO_Out→06_Alarms

All seven run in the MAST task, in that order. The safety CPU’s SAFE task stays empty: the safety I/O on the board isn’t used by this demo. Only the two orange sections name the device DDTs Control Expert generates (SIG300, ATV930, and the RIO drop’s status), so they are the only ones we edit for our project. The others work on plain variables.

FileDoes
00_IO_Map.stCopies the SIG300 and ATV930 device-DDT inputs (health bits, input bytes, ETA, RFRD, LCR, OTR, THR, LFT) and the RIO drop’s health and ring status into plain variables. Ships “unmapped” (health FALSE) so it compiles and nothing runs.
01_MPB10_Decode.stTurns the 20 IO-Link bytes into mm/s, °C and alarm bits. Adds PLC-side limits and a shock counter. Zeroes everything when the sensor data is lost.
02_Dashboard_In.stReads the dashboard command block at %MW1100 and runs a 1 s heartbeat watchdog.
03_ATV930_Control.stOne run latch for two sources (dashboard, animation table): last Start wins, any Stop wins. CiA402 state machine builds CMD and the speed reference.
04_Dashboard_Out.stWorks out the stack-light state (shown on the dashboard; the board has no lamps) and fills the status block at %MW1000 for the dashboard (word 29 = RIO, enable and stack-light bits, words 30–31 = ramps in use).
05_IO_Out.stWrites CMD, LFRD and the ramps into the ATV930 device DDT.
06_Alarms.stLatched alarms with acknowledge, timestamps and a 64-event history. Fills %MW1300 for the dashboard’s Alarms tab, and plain variables for anyone building a screen (section 7).
variables.csvEvery variable: name, type, located address, initial value, comment. Open it in Excel next to the Data Editor.

2Set up the ATV930 first

Do this on the drive’s keypad before the PLC gets involved. Menu names below are from the ATV900 family manuals; check them against our keypad. Our drive is an ATV930U07M3: 0.75 kW / 1 HP, 200–240 V three-phase in, 4.6 A out.

  1. Supply: 200–240 V three-phase on L1/L2/L3. It won’t run from a 120 V outlet.
  2. Motor: enter the nameplate data (power, voltage, current, frequency, speed), then run autotune. The motor’s full-load current must be 4.6 A or less. In North America that’s usually 60 Hz and about 1750 rpm for a 4-pole motor. Jog the motor from the keypad to prove the power side.
  3. Embedded Ethernet: Communication → Embedded Ethernet: IP mode Fixed, IP 192.168.20.30, mask 255.255.255.0, no gateway (or 192.168.20.10, the NOC). Power-cycle the drive so the address takes.
  4. Command and reference: Ref Freq 1 Config [Fr1] = Embedded Ethernet; Control mode [CHCF] = Not separate. That gives the CiA402 (Drivecom) profile this program uses.
  5. Local / Remote: the keypad’s LOCAL/REMOTE key must be on Remote. In Local the keypad owns the drive and the M580 can’t run it, which is the usual “it won’t start” on the day.
  6. Comms-loss response: set the Embedded Ethernet fault response to ramp stop or freewheel, so a cut cable stops the motor.
  7. STO: wire the E-stop to the STO inputs as the ATV930 safety manual shows. Confirm the drive shows “STO” when the E-stop is pressed.

The PLC is the only thing joining them: the NOC hands the drive and sensor data to the CPU across the rack. Nothing routes between the networks. The dashboard’s IP addresses tab holds the same plan; change it there and here together.

The rig reuses 192.168.10.x and 192.168.20.x, which the lab network uses too. Keep the rig on its own cables and switches and never patch it into the lab network, or addresses like .10 will clash. The cobot’s D-Link router is the exception: it joins the device network on purpose.
  1. Check Control Expert has the Safety (XLS) license (Help → About, or the license manager): only that edition offers the BMEP584040S.
  2. New project: BMEP584040S, firmware 3.10 (what the CPU reports). Control Expert adds the BMEP58CPROS3 in the next slot. If we already built the project for a BMEP584040, right-click the CPU on the PLC bus → Replace Processor instead. On the main rack add the power supply, BMENOC0311, BMXNRP0200, BMXSDI1602 and BMXSRA0405 in their real slots.
  3. CPU → IPConfig: main IP 192.168.10.10, mask 255.255.255.0, no gateway. Leave the service port (ETH1) enabled in access mode: that’s where the dashboard laptop plugs in.
  4. Add the RIO drop to the PLC bus (EIO bus): a BMEXBP1002 rack (two power supplies), the BMECRA31210, then each module in its real slot, including the BMXNRP0200 (it has no settings). Drop number 3, IP 192.168.10.20 on the drop’s IPConfig. Check the CRA’s rotary switches read drop 3 (tens 0, ones 3), changed only with the power off. The CPU hands the CRA its address at power-up.
  5. The safety modules (BMXSDI1602, BMXSRA0405 and the others) go in the configuration so the racks match. They belong to the SAFE task; we leave them unwired in the program. Assign the drop to the MAST task for the rest.
  6. BMENOC0311 → open its DTM: IP 192.168.20.10, mask 255.255.255.0, and disable the backplane port. With it enabled the NOC must share the CPU’s subnet, so Control Expert rejects .20.10. The drive and sensor still work: the NOC passes their I/O to the CPU across the rack, not over Ethernet. To reach the SIG300 and ATV930 web pages, use the D-Link Wi-Fi or plug into the NOC’s ETH1 with a 192.168.20.x address.
  7. Check the project allows located %MW memory with at least %MW1000–%MW1104 free (and %MW1200–%MW1209 for the drive bridge).
  8. Downloading to a safety CPU: it has to be in maintenance mode, not safety mode, to accept a modified program. Control Expert asks for the safety password we set in the project.

4Add the devices in the DTM Browser

SICK SIG300

  1. Check the SIG300’s type label: we need the EtherNet/IP model, SIG300-0A05AA100 (part no. 1131012), which has an EDS file. (The PROFINET and EtherCAT models can’t be scanned by the M580.)
  2. Get the EDS: sick.com → search the part number on the label → product page → Downloads → device description files → the EtherNet/IP EDS (a .zip with an .eds and an .ico). The SICK Support Portal has the same files. Unzip it into a folder of its own.
  3. DTM Browser → right-click the BMENOC0311 → Device menu → Additional functions → Add EDS to library, offline → browse to the .eds and finish. Then Tools → Hardware Catalog → DTM Catalog → Update, or the SIG300 won’t show in the Add list.
  4. DTM Browser → right-click the BMENOC0311 → Add → SIG300. Alias SIG300. (Both devices hang off the NOC, not the CPU’s embedded scanner.)
  5. Address Setting: IP 192.168.20.20, mask 255.255.255.0 (static, matches the SIG300 web UI). RPI 50 ms.
  6. Set the input connection to Point to Point (as for the ATV930), so its I/O isn’t multicast onto the D-Link’s Wi-Fi.
  7. Pick the Input Only connection: we only read the sensor, and the SIG300 keeps the port settings from its web page. (Exclusive Owner also works, but it writes the DTM’s 138-byte configuration to the SIG300 each time it connects, replacing those settings, and adds a 404-byte output block.) The input block is 404 bytes: byte 4 is port S1’s qualifier (PQI), byte 5 is reserved and bytes 6–37 are S1’s process data, so iPD_Ofs is 6.

Altivar ATV930

  1. Add the ATV930 under the same BMENOC0311, using the Altivar DTM from the Schneider DTM library (or the ATV930 EDS). Our alias is ATV9xx. IP 192.168.20.30, mask 255.255.255.0, and DHCP for this device disabled: the drive has a fixed address.
  2. Open the drive’s Protocols & Drive Profiles page:
    • EtherNet Protocol: EtherNet/IP.
    • IO Connection Profile: 100/101 Generic Altivar. It lets us choose the channels. (The 106/107 ATV9xx Solution profile has a fixed list without THR, LFT or ACC/DEC, and it writes torque, logic-output and analog-output values our program never sets.)
    • Fallback Mode: Freewheel stop, so the motor coasts to a stop if the PLC connection drops.
    • RPI 10 ms for both directions. Input Mode: Point to Point. Multicast drive data would be copied out of the NOC’s built-in switch to the SIG300 and the Wi-Fi as well.
  3. The profile and the sizes must match the drive. Ours reports assemblies 100 and 101 at 4 bytes each (ETA, RFRD, CMD, LFRD), and 106 and 107 at 12 and 24 bytes. With the path on 106/107 but sizes of 4 bytes, the connection never came up. The table below is what we want in the end; until we work out how to add channels on this drive, keep those four.
  4. Drive I/O Profile: click the Code cell of each row and pick the parameter.
    ChannelInputs (drive to controller)Outputs (controller to drive)
    1ETA status word (3201)CMD command word (8501)
    2RFRD output speed, rpm (8604)LFRD speed reference, rpm (8602)
    3LCR motor current, 0.1 A (3204)ACC acceleration, 0.1 s (9001), optional
    4OTR motor torque, % (3205)DEC deceleration, 0.1 s (9002), optional
    5THR motor thermal state, % (3209)
    6LFT last fault (7121)
    The numbers in brackets are the Altivar logical addresses; if the drop-down shows different ones, use those. Without ACC/DEC the drive keeps the ramps set on its keypad and the VFD control tab can’t change them. Worth adding as inputs 7 and 8 later: EPRW (active electrical power, for an energy talking point) and CCC (active command channel, which shows a drive stuck in Local).
  5. Build → Analyze. Control Expert generates a device DDT for each device. Open the Data Editor and expand SIG300 and ATV930 to see the element names we need in section 6.

5Variables and sections

  1. Variables: import variables.xsy (Data Editor → right-click → Import, or File → Import), which holds every row of variables.csv. If our version refuses it, create them by hand from variables.csv; after editing the CSV, python make_xsy.py rebuilds the import file.
  2. Check every row of variables.csv is there. Give aDash the address %MW1000 and aCmd %MW1100, and set the initial values shown (limits, iMaxSpeed, the placeholders).
  3. Program → Tasks → MAST → Sections: create seven ST sections, in this order: S00_IO_Map, S01_MPB10_Decode, S02_Dashboard_In, S03_ATV930_Control, S04_Dashboard_Out, S05_IO_Out, S06_Alarms. (A section name can’t start with a digit, so each gets an S in front of its file name.)
  4. Paste each file’s text into its section. Build → Analyze. It should compile with zero errors before we map anything.

6Map the devices

00_IO_Map and 05_IO_Out are already mapped to the device DDTs in our project: ATV9xx, SIG300_Revision_1_1_from_EDS and BMEP58_ECPU_EXT. If an alias changes, change it there.

xSIG300_Health := SIG300_Revision_1_1_from_EDS.Freshness;
aSIG300_In[4]  := SIG300_Revision_1_1_from_EDS.Inputs.S1_PQI;   (* and bytes 6-25, one line each *)
xATV_Health    := ATV9xx.Freshness;
wATV_ETA       := ATV9xx.Inputs.ETA;
iATV_Speed     := ATV9xx.Inputs.RFRD;
xDrop_Health   := BMEP58_ECPU_EXT.DROP_HEALTH[3];
xRing_Closed   := BMEP58_ECPU_EXT.REDUNDANCY_STATUS;

Our ATV9xx connection carries ETA, RFRD, CMD and LFRD. Add the other channels from section 4 in its DTM, build, then remove the comment marks on their lines in both sections. There is no operator panel on this board, so xDemoEnable is set from an animation table. Build, then download over USB (first time) or ETH1.

Before any download, stop the motor. The download cuts the drive’s connection, and a running drive trips ETHF (Embedded Ethernet communication interruption). Clear it with xLocalReset or the dashboard’s Fault reset. Then check xSimBridge is 0 in an animation table: left at 1 on the real PLC, the program ignores the drive, so xATV_Health stays FALSE and ETA reads 0 even with ATV9xx.Freshness at 1.
The MPB10 sends four big-endian floats (temperature, then vibration X, Y and Z) and a status word. 01_MPB10_Decode builds them from their bytes. We read that layout from the live sensor, so check it against the IODD or the SIG300 web page. Shock and the status bits aren’t decoded yet.

Timestamps come from the CPU’s clock, in %SW50–%SW53, so set it first: a CPU with an empty clock reads 1980. The dashboard’s Alarms tab warns if it isn’t set.

8Commission it, in this order

RIO drop over fiber

  1. Power both racks. The fiber link LEDs on both BMXNRP0200s come on, the CRA takes its address and xDrop_Health goes TRUE.
  2. Pull one fiber link: the drop stays healthy and xRing_Closed goes FALSE. Reconnect. Pull both: xDrop_Health goes FALSE. This is the fiber talking point for the customer.

Sensor

  1. Animation table: xSIG300_Health TRUE. Watch aSIG300_In and tap the motor: the bytes that move are the MPB10’s. Set iPD_Ofs so byte 0 of the 20 lines up with them.
  2. Check rTemperature reads room temperature at rest and rVibVelocity rises when we tap.
  3. Unplug the SIG300’s Ethernet cable: xSensorCommAlarm TRUE and the values go to 0 within a second. Reconnect.

Drive (motor uncoupled, low speed)

  1. Set iMaxSpeed to 300 for the first run. xATV_Health must be TRUE and wATV_ETA must change when we press the E-stop.
  2. Set xDemoEnable TRUE, iLocalSpeed 200, then xLocalRun TRUE. Watch ETA go 16#0040 → 16#0021 → 16#0023 → 16#0027 and iATV_Speed follow the ramp.
  3. Set xLocalRun FALSE: the motor stops on its ramp. Try xLocalReverse. Press the E-stop while running: the motor must stop no matter what the PLC says.
  4. Set xDemoEnable FALSE while running: it stops and won’t restart until a fresh Start.
  5. Raise iMaxSpeed to the demo limit: the motor’s nameplate speed or lower (about 1750 rpm for a 60 Hz 4-pole motor). Set the dashboard’s Setup → speed limit and nominal speed to match.

Dashboard

  1. Dashboard → IP addresses tab: the CPU and RIO drop show reachable; the NOC, SIG300 and ATV930 show “not from here” (they’re on the device network) and their health bits on the network tab show whether they’re talking to the PLC. Setup → Mode Live. The heartbeat counts and all boxes on the network tab go green.
  2. To let the dashboard run the motor: tick Allow drive control in Setup, then set xDashboardAllowed TRUE in the PLC. The VFD control tab lists every permissive and shows which one is blocking.
  3. On the VFD control tab: Start forward, Stop, Start reverse, then hold Jog (the PLC caps it at iJogSpeedMax). Change the ramps and watch the reference-vs-actual chart.
  4. Run the demo sequence once with the motor uncoupled and a low iMaxSpeed. It uses the same command block as the buttons, so the PLC needs nothing extra. Check that STOP and the E-stop each end it.
  5. Close the dashboard page while the motor runs: the PLC watchdog drops the run command within about 1 s.

Before the M580 is ready: the PLC simulator and the real drive

Control Expert’s PLC simulator runs our program but can’t scan the ATV930. dashboard\drive_bridge.py does the drive’s half over Modbus TCP: it sends our CMD, LFRD, ACC and DEC to the drive and writes ETA, RFRD, LCR, OTR, THR and LFT back into aBridge at %MW1200. With xSimBridge TRUE, 00_IO_Map takes the drive values from there instead of the DDT. For testing only, motor uncoupled.

  1. Free port 502 on this PC: the PLC simulator’s Modbus server needs it. Close anything else that uses it (the Lexium cobot simulator does).
  2. Make sure the real M580 isn’t scanning the drive (rack off, or NOC ETH2 unplugged): one master at a time. Patch the laptop to the drive’s Ethernet port (directly or through a small switch) and give that port an address on the device network, for example 192.168.20.100.
  3. On the drive: keypad on Remote, the command and reference channel on embedded Ethernet (as in section 2), and the communication-loss response set, so a crashed PC also stops the motor.
  4. Control Expert: PLC → Simulation mode, build, connect, download, RUN.
  5. Start the bridge: Start Drive Bridge.bat in the dashboard folder (or python drive_bridge.py). It says what it’s waiting for, once a second.
  6. Animation table: xSimBridge TRUE. The bridge says driving and xATV_Health goes TRUE. Then commission as in “Drive” above: xDemoEnable, iLocalSpeed 200, xLocalRun.
  7. The dashboard can watch too: IP addresses tab → M580 CPU 127.0.0.1, Setup → Mode Live. (It warns that 127.0.0.1 isn’t on the control network; that’s expected here.) Put the real address back afterwards.
What stops the motorHow
E-stopHard-wired to STO: works whatever the PC does.
Simulator stopped, paused or closedIts heartbeat stops; within 1 s the bridge sends a ramp stop (CMD 16#0007, LFRD 0). It won’t restart by itself: stop the run in the program, then start again.
xSimBridge set FALSEThe same ramp stop.
Bridge closed (Ctrl+C or its window)A ramp stop on the way out.
PC crash or cable pulledThe drive’s own communication-loss response.
Bridge stops talking to the simulatorThe program’s 1 s watchdog on aBridge[0] drops xATV_Health, so it stops asking for a run.

The bridge caps the speed reference at 300 rpm until we pass --max-rpm (for example python drive_bridge.py --max-rpm 1750). If the drive doesn’t answer, try --drive-unit 248 or 255. --no-ramps keeps the keypad ramps. Leave xSimBridge’s initial value FALSE, so the real M580 always uses the DDT.

9Confirm on our hardware

  • Control Expert has the Safety (XLS) license, and the project’s CPU firmware (3.10) matches the CPU.
  • The drop’s health bit and the CPU’s RIO main-ring status bit (element names in the Data Editor), and that pulling one fiber link leaves the drop running.
  • ATV930U07M3 supply is 200–240 V three-phase, the keypad is on Remote, and the motor nameplate suits a 4.6 A drive.
  • BMENOC0311 at 192.168.20.10 with its backplane port disabled builds without errors, and the drive and SIG300 health bits go TRUE.
  • Device-DDT element names for the SIG300 and ATV930 (health/Freshness bits, input and output elements).
  • That PQI bit 7 (byte 4 of the SIG300 input block) means “process data valid” on port S1. The IO-Link standard says so; the EDS doesn’t list the bits.
  • MPB10 IODD: value offsets, scaling, and alarm-bit meanings.
  • ATV930 keypad menu names, the comms-fault parameter, and whether LCR/OTR/THR/LFT (and ACC/DEC on the output side) fit in the drive’s cyclic exchange.
  • Drive bridge (simulator testing): the ATV930’s Modbus unit ID, that it accepts CMD and LFRD over Modbus TCP with the channel set to embedded Ethernet, and that the PLC simulator answers on 127.0.0.1:502.
  • The Modbus unit ID the M580 answers on (the dashboard defaults to 255; try 0 if it gets no reply).
